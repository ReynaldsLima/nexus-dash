## Symptoms

expected: On sign-in, any user's JWT `app_metadata` should be populated by the project's own `custom_access_token_hook` Postgres function -- querying `tenant_users`/`agency_users` to set `role`, `tenant_id`, and `tenant_slug` (the exact key `app/[tenant-slug]/layout.tsx` reads via `user.app_metadata?.tenant_slug`).

actual: The live Auth Hook config (`GET /v1/projects/rvkkvjitfddtbdpkupok/config/auth` via Supabase Management API) shows `hook_custom_access_token_enabled: true` but `hook_custom_access_token_uri: https://rvkkvjitfddtbdpkupok.supabase.co/functions/v1/custom-access-token` -- an HTTP hook pointing at a deployed Edge Function, NOT a `pg-functions://postgres/public/custom_access_token_hook` URI. A real test sign-in (via `admin.createUser()` + password sign-in) produced JWT `app_metadata = {"plan":"trial","provider":"email","providers":["email"],"role":"visualizador","slug":null,"tenant_id":null,"trial_ends_at":null}` -- none of which matches what the Postgres function would produce. errors: No hard runtime error surfaces to the user -- the Edge Function's DB query silently no-ops due to the nonexistent columns (likely swallowed in a try/catch or ignored error). The failure is silent/structural, not an exception.

started: The Edge Function is at version 2, last updated 2026-07-05 per Supabase dashboard metadata. ## Resolution

root_cause: The Supabase project's live Custom Access Token Auth Hook (Dashboard -> Authentication -> Hooks) was configured to call a deployed HTTP Edge Function (`custom-access-token`, not present in this repo's git history -- deployed directly to the project outside the codebase) instead of this project's own `pg-functions://postgres/public/custom_access_token_hook` (migrations 0005/0019, confirmed correctly written and previously verified firing in production on 2026-05-11). The Edge Function was unrelated boilerplate (uses foreign conventions: `plan`/`trial_ends_at`/`visualizador`, none of which exist in this project's schema or role vocabulary) that only echoed a user's pre-existing `app_metadata` rather than computing it from `tenant_users`/`agency_users`, referenced two `tenants` columns that don't exist in the live schema (silent no-op), and wrote the tenant slug under `slug` instead of `tenant_slug`. Since the app's real user-provisioning flow (`lib/actions/tenants.ts::createTenantUser`) never pre-sets `app_metadata`, and every consumer (`app/[tenant-slug]/layout.tsx`, `proxy.ts`, `app/tenants/layout.tsx`) reads role/tenant identity exclusively from JWT `app_metadata` with no DB fallback, this had locked out every real `tenant_admin`/`viewer` user on `lukseg` and `beta-test` from signing in successfully (redirected to `/login?error=no_membership`), and independently blocked the Phase 5 agency role/`agency_id` claim from ever populating. This was a known, already-logged blocker (see `.planning/phases/05-agencia-multi-cliente/deferred-items.md` and `.planning/STATE.md` Blockers section, discovered same-day during Phase 5 Plan 05-02).
fix: Remediation Option A applied by user directly in the Supabase Dashboard (project `rvkkvjitfddtbdpkupok`): Authentication -> Hooks -> Custom Access Token switched from the `custom-access-token` Edge Function to the Postgres function `public.custom_access_token_hook` (migrations 0005/0019, already correctly written, zero new code required). No repo files were changed -- this was a live project configuration change only.
