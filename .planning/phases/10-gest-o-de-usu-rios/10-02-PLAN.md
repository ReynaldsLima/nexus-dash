<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → Server Action | Any authenticated client can invoke a Server Action; role is NOT enforced by route middleware for actions |
| Server Action → auth.users (admin API) | Arbitrary email/password mutation of any user by id — highest-privilege surface in the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-01 | Elevation of Privilege | All 6 new Server Actions | mitigate | `requireSuperAdmin()` gate as the FIRST statement in every action (getUser + get_user_role via user-session client). Closes the pre-existing gap where actions trusted only route middleware. Each action has a passing "rejects non-super_admin" unit test. |
| T-10-02 | Tampering | removeTenantUserAccess / removeAgencyUserAccess DELETE | mitigate | Scope delete by BOTH keys (`tenant_id`+`user_id` / `agency_id`+`user_id`). tenant_users has no UNIQUE(user_id), so an unscoped delete could remove a user's membership in an unrelated tenant. Enforced by acceptance grep. |
| T-10-03 | Information Disclosure | get_user_role client selection | mitigate | Gate lives in auth-guard.ts (Plan 01) using `createClient()`; actions never re-implement the check via the service client. |
| T-10-08 | Tampering | editUserEmail input | mitigate | Zod validation (userId/tenantId/agencyId uuid, email `.email()`) before any admin call; V5 input validation per ASVS. |
</threat_model>
