    ```sql
    -- supabase/migrations/0023_revoke_user_sessions_function.sql
    -- Phase 10 (USER-05): admin.signOut(jwt, scope) requires the TARGET user's own JWT, which a
    -- Super Admin removing someone else's access never has. This function lets service_role revoke
    -- a specific user's sessions by ID instead. Deleting auth.sessions cascades to
    -- auth.refresh_tokens (session_id FK), preventing that user from minting a new access token.
    -- Does NOT invalidate an already-issued, unexpired access token (stateless JWT — see 10-RESEARCH.md Pitfall 2).
    CREATE OR REPLACE FUNCTION public.revoke_user_sessions(target_user_id UUID)
    RETURNS VOID
    LANGUAGE SQL
    SECURITY DEFINER
    SET search_path = public, auth
    AS $$
      DELETE FROM auth.sessions WHERE user_id = target_user_id;
      -- If Step 1 found NO cascade FK, ALSO uncomment the next line:
      -- DELETE FROM auth.refresh_tokens WHERE user_id = target_user_id;
    $$;

    REVOKE ALL ON FUNCTION public.revoke_user_sessions(UUID) FROM authenticated, anon, PUBLIC;
    GRANT EXECUTE ON FUNCTION public.revoke_user_sessions(UUID) TO service_role;
    ```
    (auth.refresh_tokens keys on user_id in current Supabase schema; if Step 1 confirms that column exists, the second DELETE is safe regardless. Prefer keeping BOTH deletes if the cascade cannot be positively confirmed — belt-and-suspenders, no downside.)

    ```typescript
    import { createClient } from '@/lib/supabase/server'

    export type GuardResult = { ok: true } | { error: string }

    /**
     * Phase 10: re-verify the caller is super_admin INSIDE each sensitive Server Action.
     * MUST use the user-session client (createClient) — get_user_role() reads request.jwt.claims,
     * which PostgREST only populates from the caller's own JWT. Calling it via the service client
     * returns NULL and would make the gate reject everyone (10-RESEARCH.md anti-pattern).
     */
    export async function requireSuperAdmin(): Promise<GuardResult> {
      const supabase = await createClient()
      const { data: { user } } = await supabase.auth.getUser()
      if (!user) return { error: 'Não autenticado.' }
      const { data: role, error } = await supabase.rpc('get_user_role')
      if (error || role !== 'super_admin') {
        return { error: 'Apenas super_admin pode executar esta ação.' }
      }
      return { ok: true }
    }
    ```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| authenticated role → revoke_user_sessions RPC | A logged-in non-super_admin could attempt to call the session-revocation function directly via PostgREST |
| stateless JWT → live sessions table | Access tokens are validated only by signature+expiry, never checked against auth.sessions on each request |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-04 | Elevation of Privilege | public.revoke_user_sessions RPC | mitigate | `REVOKE ALL FROM authenticated, anon, PUBLIC` + `GRANT EXECUTE ... TO service_role` in migration 0023; verified via `has_function_privilege('authenticated', ...)` = false (Task 1 acceptance) |
| T-10-05 | Repudiation / false sense of security | Session revocation effectiveness | mitigate | Live skip-if-no-env integration test asserts the pre-revocation refresh token can no longer mint a new access token — proves server-side EFFECT, not just "RPC was called" (Task 2) |
| T-10-06 | Information Disclosure | requireSuperAdmin via wrong client | mitigate | Guard calls `get_user_role()` on the user-session client (`createClient`), never the service client (which would silently return NULL) — enforced by Task 3 acceptance grep for absence of `createServiceClient` |
| T-10-07 | Information Disclosure | revoke_user_sessions residual token window | accept | Stateless JWTs cannot be invalidated before their `exp`; residual window bounded by project JWT expiry (Pitfall 2). Documented, not fixable in code. Confirm expiry in Plan 04 checkpoint. |
</threat_model>
