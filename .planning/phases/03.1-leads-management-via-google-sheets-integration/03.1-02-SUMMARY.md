# Phase 03.1 Plan 02: Google Sheets Write-Back Route Summary

**PATCH /api/leads/[id]/status writes a lead's status to column F of the tenant's Google Sheet via a Service Account JWT, gated by role (super_admin/tenant_admin only) and protected against range injection and credential leakage.**

## Performance

- **Duration:** ~25 min

## Accomplishments
- `lib/sheets.ts` created with `rowForId`, `statusRange`, `mapSheetsError`, `updateLeadStatus` — pure mapping/error-classification functions are unit-tested independently of I/O
- `PATCH /api/leads/[id]/status` route created, mirroring the `meta-ads/connect` auth/role-gate pattern exactly: `auth.getUser()` → 401 if absent → `get_user_role()` RPC → 403 for `viewer`/null/error → Zod body validation → explicit tenant credential select → write → mapped error response
- `id` path param validated as a non-negative integer before it is ever used to compose the Sheets A1 range (`Leads!F{row}`), closing the range-injection threat (T-03.1-03)
- Service Account JSON (`sheets_service_account`) is fetched via an explicit column select (never `.select('*')`) and never appears in any HTTP response or log statement (T-03.1-02)
- Sheets API errors (429/403/401/unknown) are classified into HTTP status + pt-BR message with **no retry logic** anywhere in the write path (D-07) — confirmed via grep during verification
- Self-skipping integration test (`tests/integration/sheets-write.test.ts`) added for optional end-to-end verification against a real test spreadsheet, following the `vault-rpc.test.ts` `describeIfEnv` pattern — does not block the local/CI suite without `GOOGLE_SHEETS_TEST_*` env vars

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] `client.fetch(url, { method, data })` does not type-check against google-auth-library's `JWT.fetch` overloads**
- **Found during:** Task 3 (running the plan's own `<verification>` step `npx tsc --noEmit` after all three tasks were implemented, per the plan's file list)
- **Issue:** `google-auth-library`'s `AuthClient.fetch<T>(...args: Parameters<Gaxios['fetch']>)` accepts either the standard 2-arg `fetch(input, init)` form OR a single `GaxiosOptions` object — it does not accept a 2-arg call where the second argument has a `data` field, since `data` isn't part of `RequestInit`. The plan's literal code block used `client.fetch(url, { method: 'PUT', data: {...} })`, which fails `tsc --noEmit`.
- **Fix:** Changed to the single-argument `GaxiosOptions` form: `client.fetch({ url, method: 'PUT', data: {...} })`. Behavior is identical (same HTTP request), only the call shape changed to match the library's actual type signature.
- **Files modified:** `lib/sheets.ts`
- **Verification:** `npx tsc --noEmit` no longer reports this error; full test suite still green (118 passed / 1 skipped)
- **Commit:** `445917b`

**2. [Rule 1 - Bug] Test mock `updateLeadStatusImpl` typed with zero params, but spread-called with 4 args**
- **Found during:** Task 3, same `tsc --noEmit` verification pass
- **Issue:** `mockState.updateLeadStatusImpl: async () => {}` was inferred as `() => Promise<void>`; the mock factory calls it as `mockState.updateLeadStatusImpl(...args)` where `args` has 4 elements (matching `updateLeadStatus`'s real signature), which `tsc` correctly rejected.
- **Fix:** Widened the mock's declared type to `async (..._args: unknown[]) => {}`, matching how it's actually invoked. No test behavior changed — the mock's return value/throw behavior per test case is unaffected.
- **Files modified:** `tests/unit/leads-status-route.test.ts`
- **Verification:** `npx tsc --noEmit` no longer reports this error; `tests/unit/leads-status-route.test.ts` still 10/10 passing
- **Commit:** `445917b`
