# Phase 03.1: Code Review Report

**Reviewed:** 2026-07-05T00:00:00Z
**Depth:** standard
**Files Reviewed:** 12
**Status:** issues_found

## Summary

Reviewed the Google Sheets leads write-back feature: the new `sheets_service_account` column/migration, the `lib/sheets.ts` write helper, the `PATCH /api/leads/[id]/status` route, the existing `GET /api/leads` route, the leads UI page, `lib/leads.ts` categorization helper, and the associated unit/integration tests.

The implementation is generally careful — id validation happens before any I/O (mitigating range injection into the Sheets API URL), the credential is never logged or returned in HTTP responses, `runtime = 'nodejs'` is correctly forced for RS256 JWT signing, error mapping has solid unit-test coverage, and the UI does optimistic updates with revert-on-failure. However, there is one critical authorization gap: the new highly-privileged write credential (`sheets_service_account`) is stored in a table whose existing row-level security policy grants read access to *any* authenticated member of the tenant (not just `super_admin`/`tenant_admin`), which is inconsistent with the route-level role gate applied to the endpoint that uses this credential.

## Critical Issues

### CR-01: `sheets_service_account` (write-capable credential) is readable by any tenant member via RLS, not just admins

**File:** `supabase/migrations/0015_add_sheets_service_account_to_tenants.sql:8`
**Issue:**
This migration adds `sheets_service_account` (a Google Service Account JSON containing a `private_key` scoped to `https://www.googleapis.com/auth/spreadsheets` — full read/write access to the tenant's spreadsheet) to `public.tenants`. No new RLS policy or column-level grant/revoke is added alongside it.

The existing policy from `0004_create_rls_policies.sql` (`tenants_member_select`) grants `SELECT` on the **entire tenant row** to any authenticated user whose `tenant_id` matches, regardless of role:
```sql
CREATE POLICY tenants_member_select ON public.tenants
  FOR SELECT TO authenticated
  USING (id = (SELECT public.get_tenant_id()) AND active = TRUE);
```
`app/api/leads/[id]/status/route.ts` enforces `role IN ('super_admin', 'tenant_admin')` at the *application* layer before it reads and uses this credential (lines 27-34, 48-53), but it does so using the user-scoped Supabase client from `lib/supabase/server.ts` (publishable/anon key + user cookies — RLS applies with the caller's own JWT). Nothing prevents a `viewer`-role user of the same tenant from bypassing the Next.js route entirely and querying PostgREST directly with their own session (e.g. `GET /rest/v1/tenants?select=sheets_service_account&slug=eq.<slug>`), since RLS only checks `tenant_id`/`active`, not role, for `SELECT`. This lets a `viewer` (whose intended access is "own tenant data, read-only" per project role model) obtain full write credentials to the Google Sheet — a privilege escalation / authorization bypass.

This is a materially bigger exposure than the pre-existing `sheets_api_key` (read-only, added in migration 0012) under the same permissive policy, because the new credential grants write access.

**Fix:** Restrict column-level access at the DB layer (PostgREST + Postgres column privileges), or move the credential to a table/RPC gated by role:
```sql
-- Option A: column-level revoke, force reads through a SECURITY DEFINER RPC
-- that itself checks get_user_role() IN ('super_admin','tenant_admin').
REVOKE SELECT (sheets_service_account) ON public.tenants FROM authenticated;

CREATE OR REPLACE FUNCTION public.get_sheets_service_account(p_tenant_id uuid)
RETURNS jsonb
LANGUAGE plpgsql
SECURITY DEFINER
SET search_path = public
AS $$
DECLARE
  v_role text := public.get_user_role();
BEGIN
  IF v_role NOT IN ('super_admin', 'tenant_admin') THEN
    RAISE EXCEPTION 'insufficient_privilege';
  END IF;
  IF v_role = 'tenant_admin' AND p_tenant_id <> public.get_tenant_id() THEN
    RAISE EXCEPTION 'insufficient_privilege';
  END IF;
  RETURN (SELECT sheets_service_account FROM public.tenants WHERE id = p_tenant_id);
END;
$$;
```
Then have `app/api/leads/[id]/status/route.ts` call this RPC instead of `.select('sheets_service_account')` directly, or switch that specific query to a service-role client after re-validating the role server-side (already done) so RLS is bypassed only in the already-role-checked code path.

## Warnings

### WR-01: Free-text `status` field allows Google Sheets formula injection via `USER_ENTERED`

**File:** `app/api/leads/[id]/status/route.ts:11`
**Issue:** The Zod schema only constrains `status` to `min(1).max(200)`:
```ts
status: z.string().min(1).max(200),
```
`updateLeadStatus` (in `lib/sheets.ts:55`) writes this value with `valueInputOption=USER_ENTERED`, which makes Google Sheets parse leading `=` (and `+`, `-`, `@`) as a formula. The UI only ever sends one of the four canonical `CATEGORY_LABELS` values (`app/[tenant-slug]/leads/page.tsx:132-143`), but the API contract itself doesn't enforce that — any `super_admin`/`tenant_admin` caller (or a compromised session with that role) can PATCH an arbitrary string such as `=IMPORTXML(...)` or `=HYPERLINK(...)` into the shared spreadsheet, which will execute for whoever opens it next (including users with more privilege than the caller, since spreadsheet access isn't scoped per-role the way the app is).
**Fix:** Restrict to the known category labels instead of free text:
```ts
status: z.enum(['Novo Lead', 'Quente', 'Negociando', 'Sem Resposta']),
```
(or import `CATEGORY_LABELS` values from `lib/leads.ts` to keep a single source of truth). If free-text status values must remain supported long-term, at minimum strip/reject leading `=`, `+`, `-`, `@` before writing, or force `valueInputOption=RAW`.

### WR-02: Unsafe type assertion on JSONB credential without runtime validation

**File:** `app/api/leads/[id]/status/route.ts:60`
**Issue:**
```ts
const sa = t.sheets_service_account as unknown as ServiceAccountCreds
```
`sheets_service_account` is an untyped `Json` column (`types/database.types.ts:291`); this line trusts its shape without validation. If the stored JSON is missing `client_email`/`private_key` (e.g. a partially-filled admin form, a copy-paste error, or a manual DB edit), the failure surfaces deep inside `google-auth-library`'s JWT signing/fetch flow and is only distinguishable from other failures via the generic `502 "Falha ao gravar na planilha."` fallback in `mapSheetsError`, making misconfiguration hard to diagnose from the client.
**Fix:** Validate the shape before use and return a clearer 404/422:
```ts
const ServiceAccountSchema = z.object({ client_email: z.string().min(1), private_key: z.string().min(1) })
const parsedSa = ServiceAccountSchema.safeParse(t.sheets_service_account)
if (!parsedSa.success) {
  return NextResponse.json({ error: 'Credencial de escrita mal configurada para este tenant' }, { status: 404 })
}
```

### IN-02: `sheetId` interpolated into the Sheets API URL without encoding

**File:** `lib/sheets.ts:55`
**Issue:**
```ts
const url = `https://sheets.googleapis.com/v4/spreadsheets/${sheetId}/values/${encodeURIComponent(range)}?...`
```
`range` is encoded but `sheetId` is not. Currently `sheetId` is admin-provisioned (not end-user input), so risk is low, but for defense-in-depth and consistency with the `range` handling, encode it too: `encodeURIComponent(sheetId)`.

### IN-03: No cancellation/cleanup for the initial leads fetch effect

**File:** `app/[tenant-slug]/leads/page.tsx:92-102`
**Issue:** The `useEffect` that fetches `/api/leads` has no `AbortController` and no unmount guard. If the component unmounts (or `slug` changes) before the fetch resolves, `setLeads`/`setError`/`setLoading` will still be called on an unmounted component, which is a harmless-but-avoidable React warning today and a latent stale-data bug if this component is ever reused with a dynamic `slug`.
**Fix:**
```ts
useEffect(() => {
  const controller = new AbortController()
  fetch(`/api/leads?tenant=${slug}`, { signal: controller.signal })
    .then(r => r.json())
    .then(d => { /* ... */ })
    .catch(e => { if (e.name !== 'AbortError') setError(e.message) })
    .finally(() => setLoading(false))
  return () => controller.abort()
}, [slug])
```

### IN-04: `cat()` keyword-priority ordering can misclassify compound statuses, with no test coverage

**File:** `lib/leads.ts:15-22`
**Issue:** `cat()` checks keyword groups in a fixed order (`negoc` → `quente` → `fim` → default `novo`) using substring `.includes()`. A status string containing overlapping wording, e.g. `"Negociação encerrada"` (negotiation that ended), matches `'negoc'` (checked first) before it can match `'fim'`'s `'encerrado'` keyword — so a closed/lost negotiation would be shown as still "Negociando" in the KPI cards and funnel. This drives the KPI counts, funnel percentages, and filter tabs on the leads page, but `lib/leads.ts` has no unit tests in this phase's test set (only `lib/sheets.ts` and the status route are covered).
**Fix:** Consider reordering checks so more specific/terminal keywords (`fim`) are evaluated before broader ones (`negoc`), or make categories mutually exclusive by keyword set, and add unit tests (e.g. `tests/unit/leads-cat.test.ts`) covering compound/ambiguous status strings.
