# Phase 03.1: Leads Management via Google Sheets integration - Context

**Gathered:** 2026-07-04
**Status:** Ready for planning

<domain>
## Phase Boundary

Visualização, triagem e gestão de leads captados via Google Sheets, por tenant, isolados via RLS existente na tabela `tenants`. Entrega:
- Página de leads (`/{tenant-slug}/leads`) com KPIs, funil de conversão e tabela filtrável/ordenável.
- Agente de IA em chat (`/{tenant-slug}/leads/agente`) para análise dos leads carregados.
- Edição do status do lead diretamente na UI, com escrita de volta na planilha Google Sheets de origem.

Este código já foi implementado fora do fluxo GSD (urgente) em 2026-05-17 e está sendo formalizado retroativamente. A discussão abaixo cobre apenas as decisões que ainda estavam em aberto — não repete o que já está implementado e aceito como está.

</domain>

<decisions>
## Implementation Decisions

### Estratégia de sincronização
- **D-01:** Manter fetch direto na Google Sheets API a cada carregamento (sem N8N/Supabase sync). Aceito como abordagem definitiva para v1 — não é um passo intermediário.
- **D-02:** Manter limite de 500 linhas (`Leads!A2:H500`) e `revalidate: 60`. Revisar apenas se algum tenant ultrapassar esse volume.

### Configuração de credenciais por tenant
- **D-03:** `sheet_id` (leitura) continua sendo preenchido manualmente via Supabase Studio/SQL pelo Super Admin — sem tela de admin nesta fase. Consistente com a constraint do projeto de "sem UI de onboarding" para 1-3 tenants.

### Edição de status do lead (nova capacidade formalizada nesta fase)
- **D-04:** A edição de status escreve de volta na planilha Google Sheets (mantém a planilha como fonte única de verdade) — não um override isolado no Supabase.
- **D-05:** Como a `sheets_api_key` atual é somente-leitura (chave simples), a escrita exige credencial nova: adicionar coluna `sheets_service_account` (JSONB) em `tenants` para armazenar a Service Account com permissão de escrita (Google Sheets API v4 `values.update`). A `sheets_api_key` existente permanece para leitura; a service account é usada apenas nas rotas de escrita.
- **D-06:** UI de edição: dropdown de status inline, direto na coluna "Status" da tabela — sem modal/drawer.
- **D-07:** Em caso de falha na escrita (rate limit, permissão negada, erro de rede): a UI reverte o dropdown para o status anterior e exibe um toast/mensagem de erro. Sem retry automático.
- **D-08:** Sem tabela de auditoria/log de mudanças de status nesta fase — o valor atual na planilha é a única fonte de verdade, sem histórico de quem mudou o quê.

### Claude's Discretion
- **Padrão de chamada à Claude API no chat de leads:** `app/api/leads/chat/route.ts` usa `fetch` raw para `api.anthropic.com` em vez de `@anthropic-ai/sdk` (padrão decidido do projeto, usado na Fase 4 — AI Insights). Usuário não definiu se deve padronizar; Claude decide durante o planning/execução se refatora para o SDK ou mantém como está, priorizando consistência com o restante do codebase sem expandir escopo desnecessariamente.
- Identificação de linha da planilha para escrita (mapeamento `id` → range da linha, ex. `Leads!F{id+2}`) é detalhe de implementação — planner/executor decide o mecanismo exato.

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `lib/leads.ts`: tipos e helpers de categorização já cobrem toda a lógica de negócio de status — a edição de status deve reutilizar `LeadCategory`/`cat()` para manter consistência visual (`CATEGORY_LABELS`, `CATEGORY_BG`).
- Tabela em `app/[tenant-slug]/leads/page.tsx` já tem coluna "Status" renderizando `<StatusBadge>` — vira o ponto de inserção do dropdown editável (D-06).

### Established Patterns
- Rotas de API sob `app/api/` fazem `createClient()` (`@/lib/supabase/server`) + `auth.getUser()` antes de qualquer query — nova rota de escrita (PATCH/PUT status) deve seguir o mesmo padrão.
- Client components fazem fetch direto para rotas internas (`/api/leads?tenant=...`), sem TanStack Query — manter consistência dentro desta fase (não introduzir TanStack Query só para o PATCH de status).

### Integration Points
- Nova rota de escrita: provavelmente `PATCH /api/leads/[id]/status` ou `PATCH /api/leads` com body `{ tenant, id, status }` — decisão de shape exata é do planner.
- Nova migration: `00XX_add_sheets_service_account_to_tenants.sql`, seguindo o padrão de `0012_add_google_sheets_to_tenants.sql`.

</code_context>

<specifics>
## Specific Ideas

- A planilha Google Sheets é e continua sendo a fonte única de verdade dos leads — nenhuma decisão nesta fase move dados para o Supabase como sistema de registro.
- Volume esperado: 1-3 tenants, cada um com até ~500 leads na planilha — todas as decisões de performance/limite partem dessa premissa.

</specifics>

<deferred>
## Deferred Ideas

- Migração da sincronização de leads para N8N → Supabase (like Google/Meta Ads) — considerada e explicitamente adiada (D-01). Reavaliar se o volume crescer ou se histórico/analytics sobre leads passar a ser necessário.
- Tela de configuração de credenciais (sheet_id/sheets_api_key/service_account) para tenants — considerada e adiada (D-03). Necessária apenas quando o produto crescer além de 1-3 tenants gerenciados manualmente.
- Auditoria/histórico de mudanças de status — considerada e adiada (D-08). Reavaliar se compliance ou necessidade de rastreabilidade surgir.
- Paginação além de 500 linhas — não solicitada pelo usuário nesta discussão; nenhuma ação necessária a menos que surja demanda real.
