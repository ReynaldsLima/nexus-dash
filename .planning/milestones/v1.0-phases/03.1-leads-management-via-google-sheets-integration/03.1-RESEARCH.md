## Summary

Esta fase formaliza um recurso que já roda em produção (leitura de leads via Google Sheets API v4 com API key, dashboard, funil e chat com IA) e adiciona uma única capacidade nova: **escrever de volta na planilha quando o Super Admin/Tenant Admin muda o status de um lead pelo dropdown inline**. A leitura usa uma API key simples (query string `?key=`), que é suficiente para `spreadsheets.values.get` em uma planilha pública/compartilhada por link — mas a Google Sheets API **não aceita API key para operações de escrita**; toda escrita exige uma identidade OAuth2 (Service Account é o padrão correto para automação servidor-a-servidor, sem tela de consentimento).

O código já lido (`app/api/leads/route.ts`, `lib/leads.ts`, páginas) confirma um dado crítico para o mapeamento de linha: o campo `Lead.id` é **o índice do array retornado por `values.get`** (`rows.map((r, i) => ({ id: i, ... }))`), não uma coluna real da planilha. Como a leitura começa em `Leads!A2`, a linha real na planilha é `id + 2`. Isso é 100% determinístico enquanto a ordem das linhas não mudar entre o carregamento da lista e o clique no dropdown — o único risco real é uma edição concorrente na planilha nesse intervalo (linha inserida/removida manualmente), que a D-08 já aceita como fora de escopo (sem histórico/auditoria, planilha é fonte única de verdade, "last write wins" é aceitável).

**Recomendação principal:** usar `google-auth-library` (não o pacote `googleapis` completo) para gerar um cliente JWT autenticado a partir do JSONB `sheets_service_account`, e chamar `client.fetch()` (ou `client.request()`) diretamente contra o endpoint REST `PUT /v4/spreadsheets/{id}/values/{range}?valueInputOption=USER_ENTERED` — mantendo o mesmo estilo "fetch direto" que já existe no path de leitura, com bundle ~150x mais leve que `googleapis`.

### Pattern 2: Autenticação Service Account com `google-auth-library` (sem `googleapis`)
**What:** Construir um cliente `JWT` a partir do objeto `sheets_service_account` (JSONB já vem parseado como objeto JS pelo `@supabase/supabase-js`/PostgREST — não é uma string a ser re-parseada) [CITED: comportamento padrão de colunas `jsonb` no PostgREST/supabase-js, confirmado no restante do projeto onde nenhuma coluna JSONB é lida com `JSON.parse` manual].
**When to use:** Toda chamada de escrita à Sheets API nesta fase.
**Example:**
```typescript
// Fonte: google-auth-library README oficial (https://github.com/googleapis/google-auth-library-nodejs)
// + Google Sheets API v4 reference (https://developers.google.com/sheets/api/reference/rest/v4/spreadsheets.values/update)
import { JWT } from 'google-auth-library'

interface ServiceAccountCreds {
  client_email: string
  private_key: string
}

async function updateLeadStatus(
  sheetId: string,
  serviceAccount: ServiceAccountCreds,
  row: number,       // linha real na planilha = id + 2 (ver Pattern 3)
  statusValue: string,
) {
  const client = new JWT({
    email: serviceAccount.client_email,
    key: serviceAccount.private_key,
    scopes: ['https://www.googleapis.com/auth/spreadsheets'], // escopo mínimo — NÃO usar 'drive' completo
  })

  const range = `Leads!F${row}` // coluna F = status, confirmado em app/api/leads/route.ts (r[5] = status, A=0,B=1,...F=5)
  const url = `https://sheets.googleapis.com/v4/spreadsheets/${sheetId}/values/${encodeURIComponent(range)}?valueInputOption=USER_ENTERED`

  return client.fetch(url, {
    method: 'PUT',
    data: { range, majorDimension: 'ROWS', values: [[statusValue]] },
  })
  // client.fetch() lança GaxiosError em respostas não-2xx — ver Common Pitfalls #3
}
```

### Pattern 3: Mapeamento `id` → linha real da planilha
**What:** `id` no `Lead` retornado pela rota GET é `i` (índice 0-based do array `rows`), e `rows` vem de `Leads!A2:H500` — ou seja, `rows[0]` é a linha 2 da planilha. Logo **linha real = `id + 2`**.
**When to use:** Sempre que a rota de escrita receber um `id` e precisar montar o range A1 (`Leads!F{row}`).
**Confidence:** HIGH — [VERIFIED: leitura direta de `app/api/leads/route.ts` linhas 25-44, `range = 'Leads!A2:H500'` e `id: i` no `.map`].
**Risco documentado (não resolvido, aceito por D-08):** se alguém editar a planilha manualmente (inserir/remover linha) entre o `GET` que populou a UI e o `PATCH` que grava o status, o `id` guardado no client pode apontar para uma linha diferente da que o usuário via ao clicar. Não há coluna de row-id estável na planilha hoje. Mitigação recomendada, mas fora do escopo declarado (D-08 aceita "última escrita vence", sem auditoria): se quisesse reduzir o risco sem violar D-08, seria possível re-ler `Leads!A{row}:E{row}` antes de escrever e comparar nome/e-mail com o valor já exibido na UI, abortando com erro "linha divergente" em caso de mismatch — **isto é uma sugestão, não uma decisão tomada; CONTEXT.md não pede essa validação e ela expande escopo.** Reportar como Open Question para o planner decidir se entra em escopo.

### Anti-Patterns to Avoid
- **Reler a planilha inteira (`A2:H500`) apenas para achar/validar uma linha antes de escrever:** desperdiça quota de leitura (300 req/min/projeto, 60 req/min/usuário) sem necessidade — o `id` já é suficiente para computar o range diretamente.
- **Usar o pacote `googleapis` completo só para um `values.update`:** peso de bundle sem ganho funcional (ver Standard Stack).
- **Guardar a Service Account em variável de ambiente (`.env`) em vez do JSONB por tenant:** quebraria o modelo multi-tenant (D-05 já decide por-tenant); além disso, variáveis de ambiente com JSON multilinha (private_key com `\n`) são a fonte mais comum de bugs de "invalid PEM"/"error:1E08010C" — armazenar em JSONB no Postgres evita esse problema específico porque o driver Postgres/PostgREST preserva a string exatamente como o JSON foi escrito, sem a camada adicional de parsing de shell/`.env` que costuma escapar `\n` incorretamente. Ver Common Pitfalls #4.

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Assinatura JWT (RS256) e obtenção/renovação de access token OAuth2 | Código manual de assinatura JWT com `crypto.sign` + chamada manual a `oauth2.googleapis.com/token` | `google-auth-library` (`JWT` class) | A biblioteca já lida com expiração/renovação de token, formatos de chave (PKCS#1 vs PKCS#8), e é mantida pelo próprio Google — reimplementar é superfície de bug em código de segurança sem necessidade. |

**Key insight:** o único componente de infraestrutura realmente novo nesta fase é a autenticação OAuth2 server-to-server — e para isso existe uma biblioteca oficial madura. Todo o resto (parsing de range A1, mapeamento de índice, categorização de status) já está implementado em `lib/leads.ts` e deve ser reutilizado, não recriado.

## Common Pitfalls

### Pitfall 1: API key não funciona para escrita
**What goes wrong:** Tentar reusar `tenant.sheets_api_key` (que já existe e funciona para leitura) na rota de escrita, e receber 401/403.
**Why it happens:** API keys da Google só autenticam chamadas a dados públicos/leitura; qualquer `values.update`/`values.append`/`batchUpdate` exige um token OAuth2 de uma identidade com permissão de Editor na planilha.
**How to avoid:** Usar exclusivamente `sheets_service_account` (nova coluna) para a rota de escrita; nunca tentar "promover" a API key.
**Warning signs:** Erro 401 "Login Required" ou 403 mesmo com a chave correta.
**Confidence:** HIGH [CITED: comportamento documentado da Google Cloud sobre API keys — só autenticam, não autorizam operações de escrita em recursos não públicos].

### Pitfall 2: Service Account não compartilhada na planilha (403 PERMISSION_DENIED)
**What goes wrong:** A chamada `values.update` retorna HTTP 403 mesmo com credenciais válidas e API habilitada.
**Why it happens:** Uma Service Account é uma identidade Google própria, sem acesso a nenhum arquivo por padrão. É necessário compartilhar a planilha (`Compartilhar` → colar o `client_email` da service account, ex. `xxx@project.iam.gserviceaccount.com`) com permissão de **Editor**.
**How to avoid:** Documentar esse passo manual como parte do runbook de setup do tenant (junto com D-03, que já é manual via Supabase Studio) — o Super Admin precisa: (1) criar a Service Account no Google Cloud, (2) baixar o JSON, (3) **compartilhar a planilha com o `client_email` como Editor**, (4) inserir o JSON em `tenants.sheets_service_account`.
**Warning signs:** `error.status === 'PERMISSION_DENIED'`, `error.code === 403`, mensagem "The caller does not have permission".
**Confidence:** HIGH [MEDIUM→HIGH: WebSearch cross-referenciado com múltiplas fontes — Google Issue Tracker, GitHub issues de bibliotecas terceiras, community forums — todas convergem no mesmo diagnóstico].

### Pitfall 3: Confundir 429 (rate limit) com 403 (permissão) na UX de erro
**What goes wrong:** D-07 pede uma mensagem clara para o usuário; se a rota não distinguir os casos, todo erro cai em uma mensagem genérica "erro ao salvar", frustrando o diagnóstico do Super Admin quando o problema é apenas quota temporária.
**Why it happens:** Ambos chegam como exceção HTTP não-2xx no cliente Node; sem inspecionar `error.response.status`/`error.response.data.error.status`, os dois parecem "um erro qualquer".
**How to avoid:** Capturar `GaxiosError` (lançado por `client.fetch()`/`client.request()`) e mapear:
  - `status === 429` → `error.response.data.error.status === 'RESOURCE_EXHAUSTED'` → mensagem "Limite de escrita da planilha atingido, tente novamente em 1 minuto" (quota documentada: **60 escritas/min/usuário e 300/min/projeto** [CITED: developers.google.com/workspace/sheets/api/limits]).
  - `status === 403` → mensagem "Sem permissão para editar a planilha — verifique se a Service Account foi compartilhada como Editor".
  - `status === 401` → token/credencial inválida — mensagem "Credencial da planilha inválida ou expirada".
  - qualquer outro (rede, 5xx) → mensagem genérica de erro de conexão, consistente com o padrão já usado no GET (`Sheets API error: {status} {text}`).
**Warning signs:** Todos os erros de escrita chegando ao toast com o mesmo texto.
**Confidence:** MEDIUM [WebFetch em docs oficiais para quota; shape de erro `{error: {code, message, status}}` é o padrão documentado da Google API Error Model (AIP-193) e confirmado por exemplos da comunidade — não foi possível provocar um erro real em ambiente de teste nesta pesquisa].

### Pitfall 4: Formato da chave privada ao inserir o JSON via Supabase Studio/SQL
**What goes wrong:** Colar o JSON da Service Account manualmente em uma query SQL (`UPDATE tenants SET sheets_service_account = '...'::jsonb`) pode corromper o campo `private_key`, que contém `\n` (quebras de linha escapadas) dentro de uma string JSON — se o editor SQL "desescapar" ou reformatar essas sequências, a chave PEM fica inválida e a assinatura JWT falha silenciosamente com erro genérico (`error:1E08010C:DECODER routines::unsupported` ou similar).
**Why it happens:** O JSON baixado do Google Cloud Console já vem com `\n` corretamente escapado como parte da sintaxe JSON válida; um editor de texto/SQL que "ajuda" reformatando quebras de linha reais quebra essa codificação.
**How to avoid:** Inserir o JSON **exatamente como baixado**, sem reformatação, preferencialmente via um cliente que trate a string como parâmetro (ex. Supabase Studio Table Editor com o campo JSON, ou um `UPDATE` parametrizado via script Node/psql com bind variable) em vez de colar dentro de uma string SQL literal editada manualmente. Se for inevitável usar SQL literal, usar dollar-quoting (`$json$...$json$`) para evitar problemas de aspas, mas isso **não** resolve o problema de quebras de linha reais vs. `\n` escapado — a integridade do JSON baixado deve ser preservada byte a byte.
**Warning signs:** Erro de assinatura JWT ("invalid_grant", "invalid signature") apesar de a Service Account e o compartilhamento estarem corretos.
**Confidence:** MEDIUM [ASSUMED — extrapolação de um pitfall extremamente comum e bem documentado para Service Accounts em variáveis de ambiente, aplicado ao cenário específico de JSONB/SQL manual desta fase, que não encontrei documentado literalmente para esse caminho exato].

### Pitfall 5: Nenhum gate de role definido para a rota de escrita
**What goes wrong:** CONTEXT.md (D-06/D-07) não menciona quem pode editar o status — se a rota não verificar role, um usuário `viewer` (role read-only por definição do projeto, AUTH-05) conseguiria escrever na planilha.
**Why it happens:** A discussão de contexto (03.1-DISCUSSION-LOG.md, inspecionado — nenhuma menção a roles) focou em UX de edição, não em quem tem permissão de editar.
**How to avoid:** Seguir o padrão já estabelecido em `app/api/meta-ads/connect/route.ts` (verificar `get_user_role()` via RPC e permitir apenas `super_admin`/`tenant_admin`, bloqueando `viewer`). Isso é consistente com AUTH-05 ("três papéis... com gates de acesso apropriados por papel") mesmo sem estar explicitado no CONTEXT.md desta fase.
**Confidence:** ASSUMED — não é uma decisão travada, é uma recomendação baseada em padrão de código existente + requisito de plataforma. **Flagged no Assumptions Log e Open Questions para confirmação do planner/usuário.**

## Code Examples

### Endpoint completo (esqueleto) combinando os padrões acima
```typescript
// app/api/leads/[id]/status/route.ts
// Fontes: padrão de app/api/meta-ads/connect/route.ts (auth/role/zod) +
// google-auth-library README (JWT) + Sheets API v4 reference (values.update)
import { NextRequest, NextResponse } from 'next/server'
import { z } from 'zod'
import { JWT } from 'google-auth-library'
import { createClient } from '@/lib/supabase/server'

export const runtime = 'nodejs' // crypto do Node é necessário para assinatura RS256

const BodySchema = z.object({
  tenant: z.string().min(1),
  status: z.string().min(1).max(200),
})

export async function PATCH(req: NextRequest, { params }: { params: Promise<{ id: string }> }) {
  const { id } = await params
  const rowIndex = Number(id)
  if (!Number.isInteger(rowIndex) || rowIndex < 0) {
    return NextResponse.json({ error: 'id inválido' }, { status: 400 })
  }

  const supabase = await createClient()
  const { data: { user } } = await supabase.auth.getUser()
  if (!user) return NextResponse.json({ error: 'Unauthorized' }, { status: 401 })

  const parsed = BodySchema.safeParse(await req.json().catch(() => null))
  if (!parsed.success) {
    return NextResponse.json({ error: 'Body inválido' }, { status: 400 })
  }
  const { tenant: tenantSlug, status } = parsed.data

  // Role gate — ver Common Pitfalls #5 (recomendação, confirmar com planner)
  const { data: role } = await supabase.rpc('get_user_role')
  if (role !== 'super_admin' && role !== 'tenant_admin') {
    return NextResponse.json({ error: 'Sem permissão para editar leads' }, { status: 403 })
  }

  const { data: t, error: tErr } = await supabase
    .from('tenants')
    .select('sheet_id, sheets_service_account')
    .eq('slug', tenantSlug)
    .eq('active', true)
    .single()

  if (tErr || !t?.sheet_id || !t?.sheets_service_account) {
    return NextResponse.json({ error: 'Planilha ou credencial de escrita não configurada' }, { status: 404 })
  }

  const sa = t.sheets_service_account as { client_email: string; private_key: string }
  const client = new JWT({ email: sa.client_email, key: sa.private_key, scopes: ['https://www.googleapis.com/auth/spreadsheets'] })

  const row = rowIndex + 2 // A2 é o início do range de leitura — ver Pattern 3
  const range = `Leads!F${row}`
  const url = `https://sheets.googleapis.com/v4/spreadsheets/${t.sheet_id}/values/${encodeURIComponent(range)}?valueInputOption=USER_ENTERED`

  try {
    await client.fetch(url, { method: 'PUT', data: { range, majorDimension: 'ROWS', values: [[status]] } })
    return NextResponse.json({ success: true })
  } catch (e: any) {
    const gStatus = e?.response?.status
    const gCode = e?.response?.data?.error?.status
    if (gStatus === 429 || gCode === 'RESOURCE_EXHAUSTED') {
      return NextResponse.json({ error: 'Limite de escrita da planilha atingido. Tente novamente em 1 minuto.' }, { status: 429 })
    }
    if (gStatus === 403 || gCode === 'PERMISSION_DENIED') {
      return NextResponse.json({ error: 'Sem permissão para editar a planilha. Verifique o compartilhamento da Service Account.' }, { status: 403 })
    }
    return NextResponse.json({ error: 'Falha ao gravar na planilha.' }, { status: 502 })
  }
}
```

### Known Threat Patterns for este stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|-----------------------|
| Exposição acidental de `sheets_service_account` (private key) em resposta de API ou log | Information Disclosure | Nunca fazer `.select('*')` na tabela `tenants` em rotas que retornam dados ao client — sempre `.select('sheet_id, sheets_api_key')` (leitura) ou `.select('sheet_id, sheets_service_account')` (server-side apenas, nunca repassado na resposta JSON da rota). A rota de escrita já segue esse padrão no exemplo de código acima (nunca retorna `sa` na resposta). |
| `viewer` conseguindo escrever status via chamada direta à rota (bypass de UI) | Elevation of Privilege | Role gate server-side (Pitfall 5/A1) — nunca confiar apenas em esconder o dropdown na UI, a rota precisa rejeitar explicitamente. |
| SSRF/range injection via `id` não validado compondo a URL da Sheets API | Tampering | `id` validado como inteiro (`Number.isInteger`, `>= 0`) antes de ser usado para montar `Leads!F{row}` — a URL base (`sheets.googleapis.com/v4/spreadsheets/{sheetId}`) já vem do banco (não do input do usuário), então o único vetor de injeção seria o componente de range, mitigado pela validação de `id`. |
| Rate limit da Sheets API esgotado por um bug de retry/loop acidental | Denial of Service (contra o próprio tenant) | D-07 já proíbe retry automático — reforça a mitigação. Nenhum polling/retry deve ser adicionado sem lógica de backoff explícita. |
